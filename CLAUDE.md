# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

shellsync is a Rust CLI (edition 2024) that turns one TOML file (`~/.config/shellsync/config.toml`) into native zsh, nushell and PowerShell 7 startup code and hooks it into each shell. The README describes user-facing behaviour and the config format in full; keep it in sync when behaviour changes.

## Commands

```sh
cargo build
cargo test                                  # unit tests + end-to-end tests
cargo test splice                           # one test, by name substring
cargo test --test shells nu_end_to_end      # one end-to-end test
cargo test --bins                           # unit tests only (no shell sessions; build still parses with installed shells)
SHELLSYNC_REQUIRE_SHELLS=1 cargo test       # a missing shell fails instead of skipping (CI sets this)
cargo clippy --locked --all-targets -- -D warnings   # as in CI, together with `cargo fmt --check`
# CI also runs clippy with --target x86_64-pc-windows-msvc (no linker needed); locally do that in the Rust Docker image
cargo run -- print zsh --config examples/example.toml   # inspect generated output
GITLAB_HOST=git.flatenet.de glab ci lint .gitlab-ci.yml   # validate CI changes before pushing
ci/release.sh check                         # Cargo.toml, CHANGELOG.md (and in CI the tag) agree on a release
```

The end-to-end tests in `tests/shells.rs` run `shellsync install` into a throwaway `HOME` under the temp dir, then start real `zsh -i` / `nu` / `pwsh` processes (always with a cleared environment: the developer's `XDG_*` and `ZDOTDIR` point at real dotfiles, so a manual run with only `HOME` changed would install into them) and check the resulting env, PATH and aliases. Without `SHELLSYNC_REQUIRE_SHELLS`, a test skips (prints a note) if its shell isn't installed. nushell's config location differs per platform (`~/Library/Application Support/nushell` on macOS without `XDG_CONFIG_HOME`), so tests ask `nu` for it instead of hard-coding a path. Each test works in a `Sandbox`: on Unix a fake `HOME` with a real `install`; on Windows the real home (nushell takes it from the system, not from `USERPROFILE`), with `SHELLSYNC_CONFIG`/`XDG_CACHE_HOME` pointing into the sandbox and the hook blocks written there with `shellsync hook`, then passed to the shells (`nu --env-config/--config`, `pwsh -NoProfile` + dot-source). Tests that run `install` first check with `shellsync paths` that every path is inside the sandbox; keep it that way.

Windows can be tested over SSH on the runner machine as the non-admin `gitlab-ci` user (`ssh gitlab-ci@192.168.179.81`, PowerShell 7 as the SSH shell). Work only in `%USERPROFILE%\shellsync-dev` (copy the tree with `git ls-files -co --exclude-standard -z | tar --null -T - -czf …`), set `CARGO_HOME` there (the machine-wide `C:\Rust` isn't writable), and never run `install` there outside a sandbox.

CI (`.gitlab-ci.yml`, remote is a self-hosted GitLab at `git.flatenet.de`): `secrets` (gitleaks) and `lint` first, then `test:linux` (Docker, pinned Rust image, Debian zsh, nushell and PowerShell release tarballs pinned by version and SHA-256; PowerShell needs `libicu76`) `test:macos` (shell executor on the developer's Mac, tag `macos`, uses whatever Homebrew has installed) and `test:windows` (shell executor running PowerShell as the `gitlab-ci` user, tag `windows`; Rust in `C:\Rust`, nushell and PowerShell 7.6 MSI installed machine-wide, not pinned). Image tags are pinned to explicit versions. On `v*` tags (and by hand, as a dry run, on the default branch) `build:*` jobs build `x86_64-unknown-linux-musl` in the Rust image, `aarch64-apple-darwin` on the Mac and `x86_64-pc-windows-msvc` on the Windows runner (static CRT via `RUSTFLAGS`), and `release` runs `ci/release.sh publish`: uploads the binaries and `SHA256SUMS` to the generic package registry with `CI_JOB_TOKEN` and creates the GitLab release from the `CHANGELOG.md` section. It never replaces an uploaded file, so it is safe to re-run. The release steps for the user are in the README under Development. For new tools on the Windows runner, ask the user to install them machine-wide (winget `--scope machine`, or the MSI: the runner and SSH sessions can't use per-user or MSIX installs).

Project state lives in `STATUS.md`; user-facing changes go into `CHANGELOG.md` under `[Unreleased]`.

## Architecture

The pipeline is: TOML → `Config` → per-shell source text → cached files that shell hooks `source`.

- `src/config.rs`: the config model and parser. It walks a `toml::Table` by hand rather than using serde derive so that errors name the exact key (`env.X.fish`, `path.prepend[0]`) and key order is preserved (an env var may reference one defined above it). `Value` is either `All(String)` or `PerShell(BTreeMap<Target, String>)`, where a `Target` is one shell or `Sh` (every shell with `Shell::is_sh()`); a shell's own key beats `sh`, and a shell not covered skips the entry. `init` blocks don't override each other: `Entries::init(shell)` joins every block covering the shell, in file order. `Config` = top-level `Entries` plus `Vec<Tool>`; a `Tool` (`[tool.X]`) has its own `Entries` and `Condition`s (`Command` on PATH, `Executable` path, `Exists` path). The `section()` parser is shared by both levels.
- `src/probe.rs`: evaluates `Condition`s at build time against the current environment (`Probe::from_env`; tests use `Probe::with_vars` and real temp files). Only used for shells whose `Dialect::guard` returns `None`, and only when the build wasn't given the shell's own answer (`Checks::Now` vs `Checks::Found`).
- `src/template.rs`: parses `~`, `$NAME`, `${NAME}`, `$$` in env/path values into `Seg::Lit`/`Seg::Var`. Variables are emitted as references in each shell's syntax and resolved at shell start, not at build time.
- `src/shell/mod.rs`: the `Shell` enum (`name()` is the config key; `parse()` also accepts CLI aliases like `nushell`; `files()` lists the generated files and which `Parts` (env, path, interactive) go into each: zsh `env.zsh` = env + path, `init.zsh` = path again + aliases + init; nu one `init.nu`, pwsh one `init.ps1`, each with everything) and the shared renderer. `render_with::<D: Dialect>` decides each tool once, then writes every file in this order: top-level entries of its parts; one block per `[tool]` in file order (skipped if empty for those parts); top-level init last (interactive parts only). It asks the shell's `Dialect` for each line. `Dialect::guard` either wraps a tool block in a startup check (zsh: builtins only, no fork) or returns `None` (nushell, which defines aliases at parse time), and then the build decides per `Checks`: `Found` is the list the shell checked itself (`build --nu-tools ...`), `Now` checks with the `Probe` (see `Decider`: PATH as the shell will have it, i.e. process PATH, plus `[path]`, plus the path entries of earlier tools that applied). `render` returns the files' text plus the tools that applied.
- `src/shell/pwsh.rs`: aliases become functions (`function g { git @args }`, PowerShell aliases can't take arguments), after removing a built-in alias of that name; guards use helper scriptblocks (`HELPERS`, written before the first guarded block via `Dialect::guard_helpers`, removed after the last). The profile hook resolves a symlinked config (`ResolveLinkTarget`) before comparing times.
- `src/shell/nu.rs` also writes `tools.nu` (`tools_check`): the nu tool conditions as nushell code, with the env/path lines they may depend on, evaluating to `{built: [...], found: [...]}`. The `env.nu` hook sources it in its own scope at every start (about 0.4 ms for 10 tools, measured with hyperfine) and runs `build --nu-tools ...$found` when `found != built`. Since the build then uses nushell's answer as given, it can't loop.
- `src/shell/<shell>.rs`: everything specific to one shell: its `Dialect` impl, quoting/escaping, hook bodies and where its startup files are. Alias bodies are passed through verbatim as shell code; only env/path values go through templating. Adding a shell means a new module, a `Shell` variant, a `render` match arm, and `HookFile` variants.
- `src/hooks.rs`: shell-independent hook handling: the `# >>> shellsync >>>` markers, `HookFile` (one per startup file; `block()` wraps the shell module's body), `files()` (where they go on this machine) and `splice`/`update_file`.
- Windows: `home()` is `USERPROFILE`; `Probe` finds commands through PATHEXT; pwsh's tool helpers and PATH dedup (case-insensitive) differ per platform (`cfg!(windows)` at generation, which runs on the machine that uses the files); `~` in nu values is `$nu.home-dir` there (nushell sets no `HOME`); the pwsh profile location comes from `pwsh` itself (Documents may be redirected); `hooks::files()` leaves out zsh; `edit` runs the editor via `cmd /S /C` with `raw_arg`. `.gitattributes` keeps LF in Windows checkouts.
- `src/main.rs`: hand-rolled argument parsing, `Paths` and path resolution (`--config`/`$SHELLSYNC_CONFIG`/XDG), `generate` (every output file, shared by `build` and `check`), `build` and staleness, `check`, `install`/`uninstall`/`edit`. `parse_all` writes outputs into a private temp dir and parses each file with `Shell::syntax_check` (`zsh -f -n`, `nu-check`); zsh alias bodies are parsed on their own (`Dialect::alias_snippet`), since `zsh -n` doesn't parse them. If a file fails, each `shell::snippets` entry (alias bodies, init blocks, with their config keys) is parsed alone to name the culprit. A shell not on PATH is skipped (looked up with `Probe`, because on Linux a missing program can look like exit 127). `check` parses the outputs with every tool applied (`Checks::Found`), `build` the ones it is about to write.

Key invariants that span the Rust code and the generated shell hooks:

- **Staleness is mtime equality, not "newer".** `build` stamps each output with the config's mtime (taken *before* reading the config). `is_stale` in Rust (all outputs), the zsh `.zshenv` hook (`-nt` both ways on `env.zsh`), the pwsh profile hook (`LastWriteTimeUtc -ne` on `init.ps1`) and the nu hook (`ls ... modified !=` on `init.nu`) must all apply the same rule, comparing the time of the file a symlinked config points to (covered by `symlinked_config_does_not_rebuild_every_start`). Change one, change all.
- **The fast path spawns no process.** Hooks compare timestamps with shell builtins and only call the binary when stale. Don't add work to the hooks that forks.
- **No cmdlets in generated PowerShell code or the pwsh hook.** The first use of a cmdlet (`Test-Path`, `Get-Item`, `Join-Path`, `Select-Object`, `Remove-Item`, …) autoloads its module, about 100 ms per start; use .NET (`[IO.File]::Exists`) and the language instead. Measured with hyperfine: the hook plus 10 aliases and 10 tools add about 45 ms to a 170 ms pwsh start, mostly one-time compile/binder cost.
- **Errors keep the last good build.** On a config error, or if an installed shell can't parse the generated code, existing outputs are left untouched and nothing is written (for either shell). Parsing spawns `zsh -f -n`, `nu -n` and `pwsh -NoProfile` (no startup files, so no hook recursion) and makes a rebuild take about 35 ms instead of 2 ms (about 235 ms with pwsh installed, mostly its startup); it only runs when stale. Covered by `edits_are_picked_up_and_errors_keep_last_good_config`.
- **No backward compatibility yet.** shellsync isn't installed anywhere, so the hook format, generated files and config schema can change freely; no migration code or compatibility shims.
- **Hooks must not break a shell when the binary is missing** (dotfiles synced to a machine without shellsync): the zsh hook checks `-x $exe`, the pwsh hook `[IO.File]::Exists`, the nu env hook wraps the build in `try`, and `config.nu` uses `source (if (… | path exists) {…} else { null })`, which nushell evaluates at parse time. Covered by `shells_start_quietly_without_the_binary`.
- **Outputs are written atomically** (temp file + rename) **with mode 0600**, since the config may hold secrets. Hook edits to dotfiles are written in place instead, so symlinked dotfiles stay symlinks.
- **nushell split:** the rebuild check lives in `env.nu` and `config.nu` only does `source`, because nushell parses `config.nu` completely before running it, so the sourced file must already exist; `env.nu` runs first and can build it. The same applies to the `[tool]` re-check: a rebuild in `env.nu` takes effect in the same start. `source` paths must be constant, hence `source (if (… | path exists) {…} else { null })` for both `init.nu` and `tools.nu`.
- **zsh split:** `.zshenv` (every zsh, also scripts) sources `env.zsh` and rebuilds only if `[[ -o interactive ]]`, so scripts never fork the binary or print config errors; `.zshrc` only sources `init.zsh`. `init.zsh` repeats the path lines because macOS login shells run `path_helper` (`/etc/zprofile`) between the two and move earlier entries to the end; `typeset -U` makes the repeat idempotent. Covered by `zsh_scripts_get_the_environment_only` and `zsh_login_shells_keep_path_order`.
- **Hooks are portable:** paths under `$HOME` are written as `~/...` (nu) or `"${HOME}/..."` (zsh, pwsh) via each shell module's path quoting and `shell::home_relative`, so synced dotfiles work on machines with a different home path. `HookFile::block()` takes the binary path and home directory as parameters, so unit tests can pin its exact output; `--exe` sets the binary for `install`/`hook` (for dotfile templates).
- **Hook blocks** are delimited by `# >>> shellsync >>>` / `# <<< shellsync <<<`; `splice` replaces, appends or removes the block and must stay idempotent (covered by `install_is_idempotent_and_uninstall_restores`). A start marker without an end marker is an error, never a guess.

`examples/example.toml` is embedded with `include_str!` and written as the starter config by `install`/`edit`, so edits to it change what new users get.

The only dependency is `toml` (with `preserve_order`, which the parser relies on for key order).

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

shellsync is a Rust CLI (edition 2024) that turns one TOML file (`~/.config/shellsync/config.toml`) into native zsh, bash, nushell and PowerShell 7 startup code and hooks it into each shell. The README describes user-facing behaviour and the config format in full; keep it in sync when behaviour changes.

## Commands

```sh
cargo build
cargo test                                  # unit tests + end-to-end tests
cargo test splice                           # one test, by name substring
cargo test --test shells nu_end_to_end      # one end-to-end test
cargo test --bins                           # unit tests only (no shell sessions; build still parses with installed shells)
SHELLSYNC_REQUIRE_SHELLS=1 cargo test       # a missing shell fails instead of skipping (CI sets this)
cargo clippy --locked --all-targets -- -D warnings   # as in CI, together with `cargo fmt --check`
# CI also runs clippy with --target x86_64-pc-windows-msvc (no linker needed); locally do that in the Rust Docker image
cargo run -- print zsh --config examples/example.toml   # inspect generated output
GITLAB_HOST=git.flatenet.de glab ci lint .gitlab-ci.yml   # validate CI changes before pushing
ci/release.sh check                         # Cargo.toml, CHANGELOG.md (and in CI the tag) agree on a release
```

The end-to-end tests in `tests/shells.rs` run `shellsync install` into a throwaway `HOME` under the temp dir, then start real `zsh -i` / `bash -i` / `nu` / `pwsh` processes (always with a cleared environment: the developer's `XDG_*` and `ZDOTDIR` point at real dotfiles, so a manual run with only `HOME` changed would install into them) and check the resulting env, PATH and aliases. Without `SHELLSYNC_REQUIRE_SHELLS`, a test skips (prints a note) if its shell isn't installed. nushell's config location differs per platform (`~/Library/Application Support/nushell` on macOS without `XDG_CONFIG_HOME`), so tests ask `nu` for it instead of hard-coding a path. Each test works in a `Sandbox`: on Unix a fake `HOME` with a real `install`; on Windows the real home (nushell takes it from the system, not from `USERPROFILE`), with `SHELLSYNC_CONFIG`/`XDG_CACHE_HOME` pointing into the sandbox and the hook blocks written there with `shellsync hook`, then passed to the shells (`nu --env-config/--config`, `pwsh -NoProfile` + dot-source, Windows PowerShell 5.1 (`powershell`, Windows only) the same with `-ExecutionPolicy RemoteSigned`, since by default it runs no scripts; `HOME` is the sandbox, which is bash's home and its `.bashrc`). Tests that run `install` first check with `shellsync paths` that every path is inside the sandbox; keep it that way. Config edits go through `Sandbox::edit_config`, which dates each version at least a second after the previous one (bash 3.2 compares whole seconds). zsh tests are skipped on Windows; there `windows_bash_end_to_end` runs Git Bash, MSYS2 and Cygwin from their default install paths (`WINDOWS_BASHES`), whose HOME shows as `/c/...`, `/tmp/...` (Git Bash maps the temp dir) or `/cygdrive/c/...`, so it compares against what bash reports.

Machine-specific notes for the maintainer (how to reach the CI runners) live in `CLAUDE.local.md`, which is not committed; this repository is mirrored publicly to GitHub, so keep host names, addresses and accounts of the private infrastructure out of committed files.

CI (`.gitlab-ci.yml`, remote is a self-hosted GitLab at `git.flatenet.de`): `secrets` (gitleaks) and `lint` first, then `test:linux` (Docker, pinned Rust image, Debian zsh and bash 5, nushell and PowerShell release tarballs pinned by version and SHA-256; PowerShell needs `libicu76`) `test:macos` (shell executor on the developer's Mac, tag `macos`, uses whatever Homebrew has installed, and the system's bash 3.2) and `test:windows` (shell executor running PowerShell as the `gitlab-ci` user, tag `windows`; Rust in `C:\Rust`, nushell, PowerShell 7.6 MSI, Windows PowerShell 5.1 (the system's), Git for Windows, MSYS2 (`C:\msys64`, tightened so only admins can write; its `/tmp` is `C:\msys64\tmp`) and Cygwin (`C:\cygwin64`) installed machine-wide, not pinned). Image tags are pinned to explicit versions. On `v*` tags (and by hand, as a dry run, on the default branch) `build:*` jobs build `x86_64-unknown-linux-musl` in the Rust image, `aarch64-apple-darwin` on the Mac and `x86_64-pc-windows-msvc` on the Windows runner (static CRT via `RUSTFLAGS`), and `release` runs `ci/release.sh publish`: uploads the binaries and `SHA256SUMS` to the generic package registry with `CI_JOB_TOKEN` and creates the GitLab release from the `CHANGELOG.md` section; then `release:github` runs `ci/release.sh github`: waits until the push mirror has the tag on GitHub (`GITHUB_REPOSITORY`, at the pipeline's commit), creates the release there as a draft with `GITHUB_TOKEN` (protected, masked variable), uploads the same files and publishes it. Neither ever replaces an uploaded file, so both are safe to re-run. The release steps for the user are in the README under Development. For new tools on the Windows runner, ask the user to install them machine-wide (winget `--scope machine`, or the MSI: the runner and SSH sessions can't use per-user or MSIX installs).

Project state lives in `STATUS.md`; user-facing changes go into `CHANGELOG.md` under `[Unreleased]`.

## Architecture

The pipeline is: TOML → `Config` → per-shell source text → cached files that shell hooks `source`.

- `src/config.rs`: the config model and parser. It walks a `toml::Table` by hand rather than using serde derive so that errors name the exact key (`env.X.fish`, `path.prepend[0]`) and key order is preserved (an env var may reference one defined above it). `Value` is either `All(String)` or `PerShell(BTreeMap<Target, String>)`, where a `Target` is one shell, `Sh` (every shell with `Shell::is_sh()`) or `Ps` (`Shell::is_ps()`: pwsh and powershell); a shell's own key beats `sh`/`ps`, and a shell not covered skips the entry. `init` blocks don't override each other: `Entries::init(shell)` joins every block covering the shell, in file order. `Config` = top-level `Entries` plus `Vec<Tool>` plus `edit_command` (`[edit] command`, top level only, used by `shellsync edit` and nothing else); a `Tool` (`[tool.X]`) has its own `Entries` and `Condition`s (`Command` on PATH, `Executable` path, `Exists` path). The `section()` parser is shared by both levels.
- `src/probe.rs`: evaluates `Condition`s at build time against the current environment (`Probe::from_env`; tests use `Probe::with_vars` and real temp files). Only used for shells whose `Dialect::guard` returns `None`, and only when the build wasn't given the shell's own answer (`Checks::Now` vs `Checks::Found`).
- `src/template.rs`: parses `~`, `$NAME`, `${NAME}`, `$$` in env/path values into `Seg::Lit`/`Seg::Var`. Variables are emitted as references in each shell's syntax and resolved at shell start, not at build time.
- `src/shell/mod.rs`: the `Shell` enum (`name()` is the config key; `parse()` also accepts CLI aliases like `nushell`; `files()` lists the generated files and which `Parts` (env, path, interactive) go into each: zsh `env.zsh` = env + path, `init.zsh` = path again + aliases + init; bash one `init.bash`, nu one `init.nu`, pwsh one `init.ps1`, powershell one `init-ps5.ps1`, each with everything; `bom()` is what a file starts with on disk, a UTF-8 BOM for powershell, added when writing, not by `render`/`print`) and the shared renderer. `render_with::<D: Dialect>` decides each tool once, then writes every file in this order: top-level entries of its parts; one block per `[tool]` in file order (skipped if empty for those parts); top-level init last (interactive parts only). It asks the shell's `Dialect` for each line. `Dialect::guard` either wraps a tool block in a startup check (zsh, bash: builtins only, no fork) or returns `None` (nushell, which defines aliases at parse time), and then the build decides per `Checks`: `Found` is the list the shell checked itself (`build --nu-tools ...`), `Now` checks with the `Probe` (see `Decider`: PATH as the shell will have it, i.e. process PATH, plus `[path]`, plus the path entries of earlier tools that applied). `render` returns the files' text plus the tools that applied.
- `src/shell/bash.rs`: compatible with bash 3.2 (macOS). Reuses zsh's quoting. No `typeset -U`, so the PATH line rebuilds PATH with a builtin-only dedup loop; `[tool]` commands are found by a helper function that walks PATH (`type -P` also reports files that can't run), written like pwsh's via `Dialect::guard_helpers`. `bash -n` runs with `-O extglob`, since init code may enable it on an earlier line.
- `src/shell/pwsh.rs`: aliases become functions (`function g { git @args }`, PowerShell aliases can't take arguments), after removing a built-in alias of that name; guards use helper scriptblocks (`HELPERS`, written before the first guarded block via `Dialect::guard_helpers`, removed after the last). The profile hook resolves a symlinked config (`ResolveLinkTarget`) before comparing times.
- `src/shell/nu.rs` also writes `tools.nu` (`tools_check`): the nu tool conditions as nushell code, with the env/path lines they may depend on, evaluating to `{built: [...], found: [...]}`. The `env.nu` hook sources it in its own scope at every start (about 0.4 ms for 10 tools, measured with hyperfine) and runs `build --nu-tools ...$found` when `found != built`. Since the build then uses nushell's answer as given, it can't loop.
- `src/shell/powershell.rs`: Windows PowerShell 5.1 (`powershell.exe`, Windows only, so its code doesn't depend on the build platform: PATHEXT helpers, case-insensitive PATH dedup). Reuses pwsh's quoting, env, alias and PATH lines (`pwsh::path_line`); its own tool helpers (no `Path.Join`; paths joined as strings, since .NET Framework's `Path.Combine`/`GetExtension` throw on a `"` in a PATH entry), `exists` check, hook, profile lookup (asks `powershell`, answer as UTF-16 code units since it writes in the console code page; falls back to `Documents\WindowsPowerShell` under `home()`) and parse check. Its files need a BOM: 5.1 reads files without one in the ANSI code page. Hook paths are ASCII (`$([char]0x…)`), since the profile's encoding is unknown.
- `src/shell/<shell>.rs`: everything specific to one shell: its `Dialect` impl, quoting/escaping, hook bodies and where its startup files are. Alias bodies are passed through verbatim as shell code; only env/path values go through templating. Adding a shell means a new module, a `Shell` variant, a `render` match arm, and `HookFile` variants.
- `src/hooks.rs`: shell-independent hook handling: the `# >>> shellsync >>>` markers, `HookFile` (one per startup file; `block()` wraps the shell module's body), `files()` (where they go on this machine) and `splice`/`update_file`.
- Windows: `home()` is `USERPROFILE`; `Probe` finds commands through PATHEXT; pwsh's tool helpers and PATH dedup (case-insensitive) differ per platform (`cfg!(windows)` at generation, which runs on the machine that uses the files); `~` in nu values is `$nu.home-dir` there (nushell sets no `HOME`); the pwsh profile location comes from `pwsh` itself (Documents may be redirected); `Shell::native()` is false for zsh (and for powershell on other platforms), so `hooks::files()` leaves it out and `parse_all` doesn't parse it; Windows PowerShell's profile is hooked only if it exists (its default execution policy runs no scripts, and a profile would make it report an error at every start); bash is Git Bash, MSYS2 or Cygwin: `bash::rc_file()` is in `HOME` (which they pass on, Windows-style, as bash's home) and is hooked only if it exists, hook paths under the profile are `"${USERPROFILE}/..."` and others `C:/...` (Windows-style paths work in bash and as arguments, Cygwin doesn't convert its own; always with a `/`, since bash looks up a command name without `/` on PATH. In CI the binary is outside the profile, over SSH inside it; `windows_bash_end_to_end` covers both), and `parse_shell` never parses with WSL's `bash.exe` (`bash::is_wsl_launcher`). Parse checks run the file `Probe::find` found: `Command::new` on Windows looks in the system folders before PATH; `edit` runs the editor via `cmd /S /C` with `raw_arg`. `.gitattributes` keeps LF in Windows checkouts.
- `src/main.rs`: hand-rolled argument parsing, `Paths` and path resolution (`--config`/`$SHELLSYNC_CONFIG`/XDG), `generate` (every output file, shared by `build` and `check`), `build` and staleness, `check`, `install`/`uninstall`/`edit` (`edit` runs `[edit] command` through `sh -c`/`cmd /S /C` if the config has one, else the editor; a config that doesn't parse goes to the editor, so it can be fixed; covered by `edit_runs_the_editor_or_the_configured_command`). `parse_all` writes outputs into a private dir inside the output dir (`TempDir`; not the system temp dir, which in MSYS2/Cygwin is a `/tmp` other users can read, or may not be writable; covered by `build_does_not_use_the_temp_dir`) and parses each file with `Shell::syntax_check` (`zsh -f -n`, `bash -O extglob -n`, `nu-check`, the pwsh and powershell parsers); zsh and bash alias bodies are parsed on their own (`Dialect::alias_snippet`), since `-n` doesn't parse them. If a file fails, each `shell::snippets` entry (alias bodies, init blocks, with their config keys) is parsed alone to name the culprit. A shell not on PATH is skipped (looked up with `Probe`, because on Linux a missing program can look like exit 127). `check` parses the outputs with every tool applied (`Checks::Found`), `build` the ones it is about to write.

Key invariants that span the Rust code and the generated shell hooks:

- **Staleness is mtime equality, not "newer".** `build` stamps each output with the config's mtime (taken *before* reading the config). `is_stale` in Rust (all outputs), the zsh `.zshenv` hook (`-nt` both ways on `env.zsh`), the bash `.bashrc` hook (the same on `init.bash`; bash before 5 compares whole seconds, a documented limit), the pwsh profile hook (`LastWriteTimeUtc -ne` on `init.ps1`), the powershell profile hook (`GetLastWriteTimeUtc -ne` on `init-ps5.ps1`; .NET Framework can't resolve a symlink, so for a config that is a reparse point it runs `build --if-stale`, which applies the rule in Rust) and the nu hook (`ls ... modified !=` on `init.nu`) must all apply the same rule, comparing the time of the file a symlinked config points to (covered by `symlinked_config_does_not_rebuild_every_start`). Change one, change all.
- **The fast path spawns no process.** Hooks compare timestamps with shell builtins and only call the binary when stale. (One exception: the powershell hook with a symlinked config, about 10 ms.) Don't add work to the hooks that forks.
- **No cmdlets in generated PowerShell code or the PowerShell hooks.** The first use of a cmdlet (`Test-Path`, `Get-Item`, `Join-Path`, `Select-Object`, `Remove-Item`, …) autoloads its module, about 100 ms per start; use .NET (`[IO.File]::Exists`) and the language instead. `$ExecutionContext.InvokeCommand.GetCommand` is no way around that at startup either (about 5 ms per call); aliases are checked through the provider with a literal path (`InvokeProvider.Item.Exists('Alias:\NAME', $false, $true)`), which also works for names like `..`. Measured with hyperfine: the hook plus 10 aliases and 10 tools add about 45 ms to a 170 ms pwsh start, mostly one-time compile/binder cost. Windows PowerShell 5.1 code must also do without .NET Core APIs (`Path.Join`, `Path.Exists`, `File.ResolveLinkTarget`) and PowerShell 7 syntax (`??`, `&&`); `uses_nothing_newer_than_5_1` checks the known ones. On the Windows runner the 5.1 hook adds about 15 ms to a 205 ms start, 10 aliases about 25 ms, 10 missing tools about 80 ms (PATH × PATHEXT lookups).
- **Errors keep the last good build.** On a config error, or if an installed shell can't parse the generated code, existing outputs are left untouched and nothing is written (for either shell). Parsing spawns `zsh -f -n`, `bash -n`, `nu -n` and `pwsh -NoProfile` (no startup files, so no hook recursion) and makes a rebuild take about 35 ms instead of 2 ms (about 235 ms with pwsh installed, mostly its startup); it only runs when stale. Covered by `edits_are_picked_up_and_errors_keep_last_good_config`.
- **Compatibility follows semver from 0.1.0 on** (released and installed on the user's machines through the dotfiles, which pin the version). An incompatible change needs a new minor version (0.x) and an entry under Changed or Removed in `CHANGELOG.md`; patch releases stay compatible. Incompatible means: a config that worked stops working or means something else, or a hook block printed by an earlier version of the same minor version stops working with the new binary (what the hooks rely on: `build --config/--out-dir/--nu-tools/--if-stale`, the generated file names, the staleness rule). Configs stay readable: a newer version still reads configs written for an older one, so new keys are additions, and a key is only removed or changed in meaning with a minor version and a changelog entry. When `shellsync hook` prints something new, the dotfiles' `.chezmoitemplates/shellsync/` partials are updated together with their pinned version; their `.ci/test.sh` fails on a mismatch.
- **Hooks must not break a shell when the binary is missing** (dotfiles synced to a machine without shellsync): the zsh and bash hooks check `-x $exe`, the pwsh and powershell hooks `[IO.File]::Exists`, the nu env hook wraps the build in `try`, and `config.nu` uses `source (if (… | path exists) {…} else { null })`, which nushell evaluates at parse time. Covered by `shells_start_quietly_without_the_binary`.
- **Outputs are written atomically** (temp file + rename) **with mode 0600**, since the config may hold secrets. Hook edits to dotfiles are written in place instead, so symlinked dotfiles stay symlinks.
- **nushell split:** the rebuild check lives in `env.nu` and `config.nu` only does `source`, because nushell parses `config.nu` completely before running it, so the sourced file must already exist; `env.nu` runs first and can build it. The same applies to the `[tool]` re-check: a rebuild in `env.nu` takes effect in the same start. `source` paths must be constant, hence `source (if (… | path exists) {…} else { null })` for both `init.nu` and `tools.nu`.
- **zsh split:** `.zshenv` (every zsh, also scripts) sources `env.zsh` and rebuilds only if `[[ -o interactive ]]`, so scripts never fork the binary or print config errors; `.zshrc` only sources `init.zsh`. `init.zsh` repeats the path lines because macOS login shells run `path_helper` (`/etc/zprofile`) between the two and move earlier entries to the end; `typeset -U` makes the repeat idempotent. Covered by `zsh_scripts_get_the_environment_only` and `zsh_login_shells_keep_path_order`.
- **bash has one hook,** in `.bashrc`, which rebuilds only if `$-` contains `i` (bash also reads `.bashrc` for `ssh host command`). shellsync doesn't touch `.bash_profile`/`.profile`: creating `.bash_profile` would stop bash from reading an existing `.profile`.
- **Hooks are portable:** paths under `$HOME` are written as `~/...` (nu) or `"${HOME}/..."` (zsh, bash, pwsh, powershell; bash on Windows `"${USERPROFILE}/..."`) via each shell module's path quoting and `shell::home_relative`, so synced dotfiles work on machines with a different home path. `HookFile::block()` takes the binary path and home directory as parameters, so unit tests can pin its exact output; `--exe` sets the binary for `install`/`hook` (for dotfile templates).
- **Hook blocks** are delimited by `# >>> shellsync >>>` / `# <<< shellsync <<<`; `splice` replaces, appends or removes the block and must stay idempotent (covered by `install_is_idempotent_and_uninstall_restores`). A start marker without an end marker is an error, never a guess.

`examples/example.toml` is embedded with `include_str!` and written as the starter config by `install`/`edit`, so edits to it change what new users get.

The only dependency is `toml` (with `preserve_order`, which the parser relies on for key order).
